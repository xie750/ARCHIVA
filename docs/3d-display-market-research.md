# 3D 展示技术调研与落地建议（2026）

## 先给结论

“3D 展示”有五种不同目标：

1. **屏幕上的可交互 3D**：用户用鼠标、触摸或手机浏览器旋转、缩放和查看热点。
2. **头显空间计算**：用户通过 VR/MR 设备获得最强的单人沉浸和空间交互。
3. **裸眼 3D / 光场**：不用眼镜，靠定向视差或多视点产生立体感。
4. **LED、透明屏、纱幕和投影**：通过透视、遮挡和环境设计制造“出屏”或“悬浮”效果。
5. **体积显示 / 真光场**：让多个方向的观察者看到空间中的成像，当前仍属于高成本、低成熟度路线。

对于河南建筑数字博物馆，建议采用“**内容资产统一，展示终端分层**”的方案：

```text
摄影/扫描/建模资产
        ↓
glTF/GLB + 全景 + 纹理 + LOD + 来源授权
        ↓
Web 3D（主产品和低成本验证）
        ├─ Quest 3 / Vision Pro（高沉浸单人体验）
        ├─ 裸眼 3D LED（展厅多人观看）
        └─ 光场/透明屏/投影（特定展项）
```

真正决定“像不像现场”的因素主要是采集方式、材质、光照、镜头语言和内容叙事。引擎或显示器只能放大这些资产的质量。

## 技术路线比较

| 路线 | 效果上限 | 并发观看 | 成熟度 | 公开渠道成本（2025–2026） | 适合场景 | 主要限制 |
|---|---:|---:|---:|---:|---|---|
| Web 3D：Three.js + WebGL/WebGPU | 3.5/5 | 5/5 | 5/5 | 软件低成本；原型约 3–8 万元 | 官网、数字出版、移动端、远程展示 | 受浏览器、显卡和移动端性能影响 |
| Quest 3 / MR 头显 | 4.5/5 | 1–2/5 | 4/5 | 约 2,000–4,500 元/台，加内容开发 | 个人沉浸、空间漫游、教育体验 | 每位观众都需要设备；卫生、眩晕、运维 |
| Apple Vision Pro | 5/5 | 1/5 | 3/5 | 官方起价约 3,499 美元，地区售价另计 | 旗舰演示、设计评审、高端展项 | 设备昂贵，内容和多人运营成本高 |
| 裸眼 3D LED | 4/5（指定视区） | 5/5 | 5/5 | 屏体约 5,000–15,000 元/㎡；项目常见 30–300 万元 | 商场、发布会、展厅大客流 | 视点固定，偏离后畸变；内容要按屏体透视制作 |
| 桌面光场/多视点显示 | 4/5 | 3/5 | 3/5 | 约 1–15 万元，尺寸越大越贵 | 展柜、桌面产品、教育和数字人 | 观看距离、亮度、分辨率和视角存在折中 |
| 透明 LED / Pepper’s Ghost / 纱幕投影 | 3/5 | 4–5/5 | 4/5 | 约 10–100 万元，小型项目可更低 | 橱窗、舞台、入口装置 | 依赖暗场、背景和精确校准 |
| 全息风扇 | 2/5 | 4/5 | 4/5 | 单机约 2,000–10,000 元 | 低成本吸睛、短内容循环 | 分辨率有限，扇叶、噪声和安全防护明显 |
| 体积显示 / 真光场 | 5/5（理论） | 3–4/5 | 1/5 | 约 10 万美元级到定制项目 | 科研、品牌旗舰、局部展项 | 分辨率、颜色、亮度、供应链和维护风险 |

评分是面向本项目的工程判断，不是实验室测量；设备价格按公开起价或行业常见区间整理，最终需要按同配置 BOM 询价。

## 推荐的主技术栈

### 1. Web 3D 作为统一内容底座

当前项目已经使用 Vue 3 + Three.js，并且已有程序化建筑、GLB 加载、DRACO/KTX2 预留和 HUD 交互，这条路线适合继续投入。

- **渲染**：Three.js WebGLRenderer 作为兼容基线；检测到 WebGPU 时再启用 WebGPURenderer、GPU 粒子和更重的后处理。
- **模型**：glTF 2.0/GLB；Blender、3ds Max 或扫描结果统一导出，使用 Draco/Meshopt、KTX2、LOD 和实例化。
- **现场感**：360°全景节点、摄影测量或激光扫描；高质量照片级实验可在后期加入 Gaussian Splatting，并保留 GLB/全景降级。
- **空间总览**：CesiumJS 或 MapLibre；不要让 Cesium、Three.js、全景查看器长期同时占用多个渲染器。
- **资产服务**：对象存储 + CDN + manifest；Java 服务只返回元数据、签名 URL、版本和授权信息。

WebGPU 是增强项，不是唯一依赖。MDN 目前仍将 WebGPU 标为 Limited availability/非 Baseline，生产环境必须保留 WebGL 回退，并在 HTTPS 环境下做能力检测。

### 2. 高沉浸版本

当模型和交互在 Web 端验证以后，再把同一批 glTF 资产接入 Unity 6/OpenXR 或 Unreal Engine 5：

- **Unity 6**：适合 Quest、AR/MR、多端快速开发和交互原型。Unity Personal 在符合收入条件时免费；Pro 价格按席位计费，需按当期官方报价核验。
- **Unreal Engine 5**：适合超大场景、电影级灯光、Nanite/Lumen 和多机展陈。内容团队和高端工作站成本更高；商业授权按项目类型和收入条件核验。

保留 glTF 资产、材质命名、LOD 和场景坐标，可以降低从 Web 迁移到 Unity/Unreal 的重做成本。

## 实现成本与实验成本

以下是早期立项估算，内容复杂度、模型授权和现场施工会造成较大波动。

| 阶段 | 周期 | 交付内容 | 预算区间 |
|---|---:|---|---:|
| P0 内容验证 | 1–3 周 | 1 座建筑、1 个 GLB、旋转/缩放、热点、基础标注和性能指标 | 3–8 万元 |
| P1 生产化 Web 版本 | 3–6 周 | LOD、DRACO/KTX2、全景节点、剖切/爆炸图、数据 API、CDN、移动适配 | 累计 8–20 万元 |
| P2 头显或空间显示适配 | 4–10 周 | OpenXR 交互、手柄/手势、空间音频、设备管理和现场模式 | Unity 路线约 8–25 万元；UE5 路线约 20–50 万元 |
| P3 展厅工程 | 6–12 周 | LED/投影/光场/多机同步、结构、控制系统、安装和维保 | 约 30–300 万元以上 |

资产费用通常会超过引擎费用，尤其是历史建筑的高精度扫描、人工清理、材质复原、动画和版权授权。正式预算应把“采集、处理、授权、内容制作、硬件、安装、维保、内容更新”拆成独立项。

云和 CDN 在 P0 阶段通常只需几十到数百元/月；展厅部署后还要加入带宽、备机、现场网络和 3 年维护成本。

## 按目标选方案

### 目标 A：先把真实效果做出来

使用一台电脑或手机浏览器 + Three.js，选一座建筑完成完整闭环：

1. 实景照片/摄影测量/授权模型；
2. GLB 优化和加载；
3. 建筑构件热点、剖切或爆炸图；
4. 360°现场节点；
5. 来源、版本、授权和采集信息；
6. PC 60 fps、移动端 30 fps、首屏小于 3 秒。

这一步能验证内容是否有价值，也能为所有后续终端准备资产。

### 目标 B：单人沉浸效果最大

Quest 3 是成本和生态更平衡的试验设备；Vision Pro 适合作为旗舰演示。体验应围绕“进入建筑、观察构件、切换历史时期、查看资料”设计，避免只把网页模型原样搬进头显。

### 目标 C：展厅多人同时看到

优先评估裸眼 3D LED 或投影融合。屏体尺寸、观众距离、视区、亮度和环境光必须在内容制作前锁定。裸眼 LED 的“出屏”效果主要来自透视和遮挡设计，不能按自由绕行的 VR 模型来制作。

### 目标 D：桌面展柜的无眼镜立体

评估 Acer SpatialLabs、Sony Spatial Reality Display 或 Looking Glass。先用一台设备验证观看距离、视区、亮度和内容更新流程，再决定是否批量采购。

### 目标 E：照片级现场复现

优先采集高质量 360 全景和摄影测量资产；Gaussian Splatting 作为同一资产的增强实验。采集图片、训练数据和最终 splat 都要有授权记录，并为低端设备提供 GLB/全景降级。

## 建议的实验顺序

1. **第 1 周**：确定 1 座示范建筑、观众类型、设备终端和真实性目标；清点可用照片、图纸、模型和授权。
2. **第 2–3 周**：在现有 Vue + Three.js 中接入真实 GLB，完成热点、相机预设、全景入口和性能采样。
3. **第 4–6 周**：补齐压缩、LOD、KTX2、数据 manifest、来源追溯、移动端降级和内容缓存。
4. **第 7–12 周**：用 Quest 3 或一块裸眼/光场设备做小规模展陈试验，记录有效观看距离、单次体验时长、并发人数、帧率和故障率。
5. **试验通过后**：再确定是扩展 Web 出版、做头显展项，还是投入 LED/投影工程；所有终端继续复用同一套资产和授权数据。

## 需要提前锁定的 KPI

- 真实性：实景/扫描/复原模型的来源和精度是否可说明；
- 体验：首屏时间、帧率、交互响应、单次体验时长；
- 设备：观看距离、最佳视角、亮度、温度、MTBF 和清洁维护；
- 运营：并发人数、内容更新周期、模型版本回滚和离线可用性；
- 成本：硬件折旧、内容更新、维保、运输、税费和三年总拥有成本。

## 面向 Web 全国化的补充判断

本项目的目标不是让用户看一个孤立的 3D 模型，而是让用户沿着一条有节奏的路径“到达、观察、进入、理解、回看”：

```text
封面与地图 → 景区/城市总览 → 360°现场节点 → 建筑 3D → 构件热点/剖切
                                      ↓
                               历史时期、声音、图纸、来源
```

纯 GLB 模型容易像 CAD 浏览器；要接近真实到访感，至少要把以下内容组合起来：

- **空间真实感**：摄影测量或高质量复原模型、真实材质、合理比例和光照；
- **现场感**：授权的 360°全景节点、相邻节点跳转、环境声音和天气/时间氛围；
- **游览感**：预设镜头、平滑移动、入口/出口、视线引导、热点和可回到上一个节点；
- **理解感**：构件拆解、历史时期切换、图纸叠加、文字、音频和资料来源；
- **性能感**：低模先显示、渐进加载、当前视野优先、弱设备降级和错误恢复。

### MySQL 够不够

**够，而且应该把 MySQL 用在它擅长的地方。** 全国化后的数据要分成两类：

| 数据类型 | 典型内容 | 是否放 MySQL |
|---|---|---|
| 结构化元数据 | 省市、景区、建筑、朝代、标签、经纬度、章节、热点、模型版本、来源和授权 | 放 MySQL |
| 大型媒体资产 | GLB、纹理、全景瓦片、图片、音频、视频、PDF、点云和 splat | 不放 MySQL，放对象存储/CDN |

按一个可控的全国精选库估算：1,000–10,000 座建筑、每座几十到几百条内容和版本记录，MySQL 通常只有几 GB 以内（即使包含索引，也远小于媒体资产）。MySQL 处理百万到千万级的结构化记录没有问题；更早遇到的瓶颈通常是图片/模型下载带宽、并发访问、搜索体验和后台审核流程，而不是表容量。

媒体资产可以按三种规模估算：

| 规模 | 建筑/景区数量 | 单位媒体平均量 | 媒体总量（粗略） |
|---|---:|---:|---:|
| 试验库 | 50–100 | 0.2–1 GB | 10–100 GB |
| 全国精选库 | 1,000–5,000 | 0.3–2 GB | 0.3–10 TB |
| 高精度大规模库 | 5,000–20,000 | 1–5 GB | 5–100 TB |

这里的“单位媒体”包含不同 LOD 的 GLB、纹理、全景节点、封面、音频和衍生图，不代表每个模型文件都这么大。高精度扫描、全景节点数量、视频和是否保留原始采集文件，会让结果相差一个数量级，所以正式立项要先做 10 个样本的实测。

### 推荐的全国化架构

```text
Vue + Three.js/WebGL(WebGPU增强)
             ↓ API
Spring Boot / MySQL（元数据、版本、授权、检索条件）
             ↓ 签名 URL
对象存储（GLB/纹理/全景/图片/音视频/PDF）
             ↓
CDN（按地区和设备缓存，支持断点和长缓存）
```

建议分层：

1. **MySQL**：管理 `region → city → site → building → scene → asset → version → source`，保存文件大小、哈希、格式、LOD、授权范围和下线时间。只保存 URL、manifest 和业务关系，不保存二进制模型。
2. **对象存储**：使用 OSS、COS、S3 或自建 MinIO 保存原始资产和发布资产。原始扫描文件、编辑文件和 Web 发布文件分桶，发布桶只允许通过签名 URL 或 CDN 读取。
3. **CDN**：分发 GLB、KTX2、全景瓦片和图片；按内容哈希命名，设置长期缓存，更新时只替换 manifest。全国用户访问时，CDN 比 MySQL 横向扩容更关键。
4. **Redis（第二阶段）**：缓存热门建筑详情、排行榜、短期会话和限流；早期访问量低时可以不引入。
5. **搜索（按需）**：省市、朝代、类型和标签筛选先用 MySQL 索引；当需要全文检索、错别字、拼音、同义词和全国联想搜索时，再接 OpenSearch/Elasticsearch，不要一开始就增加复杂度。
6. **异步资产流水线**：上传后异步生成缩略图、Draco/Meshopt、KTX2、LOD、全景瓦片、媒体元数据和病毒/格式检查；审核通过后再发布 manifest。

### 什么时候需要升级 MySQL

起步阶段用单主 MySQL、定期备份和合理索引就够。出现以下信号再升级：

- 读请求持续高于单实例承载能力：加只读副本和 Redis；
- 内容按省份、租户或版本增长到数千万行：再考虑分区或拆分服务；
- 复杂全文搜索明显拖慢数据库：把搜索迁移到 OpenSearch；
- 业务需要跨地域容灾：主库、只读副本、对象存储跨区域复制和 CDN 回源策略一起设计。

无论数据库是否升级，都不要把 3D 文件、全景原图或视频直接塞进 MySQL BLOB。这样会放大备份、主从同步、恢复和 CDN 分发的成本。
